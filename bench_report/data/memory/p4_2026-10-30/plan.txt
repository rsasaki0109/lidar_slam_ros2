Change (graph_based_slam, this commit; map_save_points_per_pass, default 2,000,000; 0 = the old save):
  map_saver::voxelGridFilterStreamed: when the map is only saved (not published) and the dynamic object filter is off,
  it is not assembled. The submap clouds, each moved by its pose as before, are read once for the bounding box and the
  points per z layer of voxels, then once per pass; a pass takes a range of z layers with at most 2,000,000 points.
  The voxels and their order are those of one VoxelGrid pass over the assembled map (the same float arithmetic places a
  point; the 64-bit voxel index grows slowest with the z layer). A voxel's point is the mean of its points, summed in
  double in the submaps' order; VoxelGrid sums in float in the order of its sort, so the means differ in the last bits
  and map.pcd is no longer byte-identical. Unit tests: against VoxelGrid over the assembled map (same voxels and order,
  within 1e-4 m), against voxelGridFilterInParts for a map too large for VoxelGrid's 32-bit index, and the same bytes
  whatever the passes.

Step 2 plan (fixed 2026-10-30 before any run with it): the running backend's submap clouds without padding.
Found first (no new run): the 616 MiB of report 39.6 is not held in a 32-byte point type, as was said when this step was
chosen. GraphStateStore keeps each submap's cloud as the PointCloud2 the frontend sent: rko_lio's deskewed scan, x, y, z
FLOAT32 and 4 bytes of padding (16 bytes a point, no intensity). Oxford's 25.6 M stored points take 391 MiB; the backend
holds about 170 MiB 17 s into the run. There is no 32-byte type to halve. Without the padding a point takes 12 bytes:
25 % less, 98 MiB on Oxford.
Lossless compression was measured on 387 deskewed scans of GrandTour con-1 (Hesai, every tenth frame of its backend input,
points in the frontend's order): per axis, bytes shuffled, zstd level 1 gives 0.57 of the 16-byte size (0.76 of the
packed size); bytes shuffled without the axis split 0.60; plain zstd 0.70. It would need a codec in the store and a new
dependency. It is left for a later step.
Change: when the backend makes a submap from odometry and a scan, the scan is stored with only the fields its reader (the
conversion to PointXYZI, fromRosMsgWithOptionalIntensity) reads: x, y, z and intensity if there is one, FLOAT32, without
padding (12 or 16 bytes a point). A scan with a field of another type is stored as it is. The map_array input (the
scanmatcher frontend) is not changed.
