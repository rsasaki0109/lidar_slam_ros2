any test mission other than arc-2 is run with it).

TEST-INFORMED, AND AGAINST ITS DEVELOPMENT RULE. This configuration was found by looking at submission 5's test result
(arc-2 0.102) and running the test's arc-2 again (sensor streams only, our own outputs only, GT-free:
screen_hs_s_2026-10-28/plan.txt). On the development data it did not meet its own rule (decision_rule_HLS_G15g.txt:
mean 0.0178 against HS-G15g's 0.0174), so it is not the project's GrandTour configuration; HS-G15g stays that.
The maintainer, shown both, left the choice to the developer's recommendation (2026-10-29), which was to prepare it:
the arc-2 failure has a physical cause that every Hesai-only setting shares, the merged cloud removes it, and the
development cost (0.4 mm on the mean of 15, within the run-to-run spread of single missions) is small against it.
Whether and when it is uploaded is the maintainer's decision.

Policy
  0. Before the test runs, the configuration file is run on one development mission (spx-3) with the batch's data
     location (DATA_ROOT=/dev/shm/gt_batch: a long mission's merged bag does not fit on the disk) and must give the
     trajectory of the development run hlsr_g15g/spx-3 byte for byte (front_tum md5
     6daccfadc07535a32ed1979ec429ebe2); otherwise nothing is run.
  1. The six test trajectories are produced in one batch (p1_grandtour_batch.sh, LIDAR=hesai_points+livox_points
     IMU=stim320_imu, G_CONFIG the file above, WS=ws/rko_g35, DATA_ROOT=/dev/shm/gt_batch), with no other job on the
     machine, and packed into one zip; the md5 of every file is recorded here before the zip leaves the VM. arc-2
     must equal the diagnostic run of screen 19 (hssm_g15g, front_tum md5 0b8704d8cb47f348b36392e9031cdd7c).
  2. If the maintainer uploads it, it is uploaded once, and the scores are recorded whatever they are. Nothing is
     tuned on them.
  3. A pipeline failure is fixed and recorded; a poor trajectory because of the configuration or the rig is submitted
     as is.

Fact sheet (proposed)
  Method name: lidar_slam_ros2 (RKO-LIO frontend, GrandTour configuration HLS-G15g). Description: LiDAR-inertial
  odometry with bump-image (voxel-wise height image) and point-to-point registration, a start hold for a robot
  standing after a walking start, and a causal IMU-driven output position filter; Hesai XT-32 and Livox MID-360
  merged per scan + STIM320; frontend output only, no loop closure, no post-processing. The LiDAR choice was revised
  after a test-phase result (arc-2). Novel: yes. Real-time: yes. LiDAR: yes. IMU: yes. Camera: no. GNSS: no.
  External odometry: no.
