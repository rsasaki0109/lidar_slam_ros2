  The frontend (RKO-LIO) alone with the GrandTour configuration HS-G15g, unchanged:
    configs/sota_v7/rko_lio_grandtour_hs_G15g_2026-10-28.yaml   md5 8a285bdb261089b3c6e66ac8c957110d

  HS-G15g = HS-G15c (point-to-point terms after 3 m, causal output position filter) + after a moving start only: the
  start hold within 5 cm while the robot stands within 1 m of its start, and the output filter after a 5-s gravity
  window (HS-G15f) + the output filter's acceleration noise 0.003 and bias noise 1e-5 (decision_rule_G15f.txt,
  decision_rule_G15g.txt). It is NOT the project's global configuration G: it was chosen on GrandTour development
  missions, for the HS rig only. The submission is labelled as GrandTour-specific.
  Causal and online: each output position comes from the IMU samples and registered scans up to its own time (the
  output filter is IMU-driven with the registered positions as measurements; after a moving start it starts once
  5 s of motion have given the gravity direction, and the output before that is the registration's); no pose is
  changed afterwards.
  Rig inputs (HS): the Hesai XT-32 point cloud and the STIM320 IMU; the STIM320 frame is the base frame; extrinsics
  from the export's `transform` attributes; T_world_prism(t) = T_world_stim320(t) T_stim320_prism with box_base ->
  prism from tf_static, as in submissions 1 to 4.
  Category: LiDAR + IMU (no camera, GNSS or external odometry). Real-time: yes (node time below the mission span on
  every GrandTour development mission).

Policy
  0. Before the test runs, the configuration file is run on one development mission (spx-3) and must give the same
     trajectory, byte for byte, as the G15g check run (G15g_g15g/spx-3, front_tum md5
     ed2b2199ec81ffcf39bbee7ca4f8159d); otherwise nothing is run.
  1. The six test trajectories are produced in one batch (p1_grandtour_batch.sh, LIDAR=hesai_points IMU=stim320_imu,
     G_CONFIG the file above, WS=ws/rko_g30), with no other job on the machine, and packed into one zip; the md5 of
     every file is recorded here before the zip leaves the VM.
  2. If the maintainer uploads it, it is uploaded once as the next test-phase submission, and the scores are recorded
     whatever they are.
  3. A pipeline failure is fixed and recorded; a poor trajectory because of HS-G15g or the rig is submitted as is.
