Policy
  0. Before the test runs, the configuration file is run on one development mission (spx-3) with the batch's data
     location (DATA_ROOT=/dev/shm/gt_batch) and must give the trajectory of the development run g16_G15h_hls/spx-3
     byte for byte (front_tum md5 d4a436c07f20b947722a9bffeb794949); otherwise nothing is run.
  1. The six test trajectories are produced in one batch (p1_grandtour_batch.sh, label G15hHLS,
     LIDAR=hesai_points+livox_points IMU=stim320_imu, G_CONFIG the file above, WS=/home/user/lidar_slam_ros2,
     DATA_ROOT=/dev/shm/gt_batch), with no other job on the machine, and packed into one zip
     (comfort_test_G15hHLS.zip); the md5 of every file is recorded here before the zip leaves the VM.
  2. If the maintainer uploads it, it is uploaded once, and the scores are recorded whatever they are. Nothing is
     tuned on them.
  3. A pipeline failure is fixed and recorded; a poor trajectory because of the configuration or the rig is submitted
     as is.
  Reported besides (GT-free): each test trajectory against submission 6's (data/grandtour/G15gHLS/), rigidly aligned.

Fact sheet (proposed)
  Method name: lidar_slam_ros2 (RKO-LIO frontend, GrandTour configuration HLS-G15h). Description: LiDAR-inertial
  odometry with bump-image (voxel-wise height image) and point-to-point registration, a per-scan limit on the
  registration's roll/pitch correction of the gyro prediction, gyro bias refinement in the first 30 s after a static
  start, a start hold for a robot standing after a walking start, and a causal IMU-driven output position filter;
  Hesai XT-32 and Livox MID-360 merged per scan + STIM320; frontend output only, no loop closure, no
  post-processing. The LiDAR choice was revised after a test-phase result (arc-2). Novel: yes. Real-time: yes.
  LiDAR: yes. IMU: yes. Camera: no. GNSS: no. External odometry: no.
