ROS-free core, M7 step b: GNSS anchoring in the offline pipeline (the core engine)
Preregistered 2026-11-17, before the code exists and before any run below.

What changes
- The live adapter's GNSS path (NavSatFix receive, origin accumulator, covariance weights, stamp
  check against the odometry, pre-odometry buffer, anchor matching, yaw alignment) moves into a
  ROS-free module that the live adapter and the offline pipeline both use.
- The offline pipeline (graph_slam_offline_runner, lidarslam.backend, the core engine) gains
  use_gnss with the live parameter names and defaults: the fixes of gnss_topic in the backend
  input (or, for the core engine, in the sensor log) become GNSS anchors of the final pose-graph
  optimization, with gravity_prior_info, the yaw alignment and the GNSS projector origin, as the
  live node's doPoseAdjustment does. With use_gnss false (every default preset) nothing changes.
- The core engine records gnss_topic in the backend input it writes.

Checks without ground truth (must hold; a failure is a bug to fix, not a result)
P1. use_gnss false: graph_slam_offline_runner and the package give the M4/M5 bytes (HILTI exp14
    core run, MapsHD calibration-room 2 replay).
P2. use_gnss true on a backend input with /gnss/fix (RTK-SLAM Construction seq1 and seq2,
    bench/ms_cons, lidarslam_rtk_gnss.yaml): the ROS 2 offline runner and the package write the
    same files.
P3. The live adapter after the move: unit tests feed the same fix and odometry sequences
    (pre-odometry fixes, stamp-skew fallback, origin reset after a jump, interpolation) to the
    old inline logic (kept verbatim in the test) and to the module; same buffers, anchors and
    alignment.
