Odyssey as development data: why G22 loses to upstream RKO-LIO on H9 (written 2026-11-13, before any run below)

H9 Odyssey is scored (report chapter 64): its reference is open, so the seven drives are development data from now
on and can never again count as a blind family. G22 is 1.11 to 1.27 times upstream RKO-LIO's ATE on all seven; both
are deterministic (three identical repetitions), so one run per variant is enough.

This is a diagnosis, not a decision. Each variant is G22's parameter file for the rig (g_params_odyssey.yaml) with
one group of keys changed, run with the same fork build on the same converted bag, scored as in H9
(p8_blind_score_h9.py's ATE):
  g         G22 as sealed (must reproduce the sealed score)
  notac     without the tactical-gyro keys (max_tilt_correction_deg, gyro_bias_time_constant_sec, gyro_bias_start_sec)
  vox1      voxel_size 1.0 (upstream's default; G22 has 0.25)
  vox05     voxel_size 0.5
  noclose   without the close_scene_* keys
  jerk3     max_expected_jerk 3.0 (upstream's default; G22 has 1000)
  noinit    initialization_phase false (upstream's default)
  nocompact local_map_compact_points false
  nokp      without icp_keypoint_voxel_multiplier, min_icp_keypoints, keypoint_shortfall_voxel_multiplier
  up        every core key at upstream's default (voxel 1.0, min_range 1.0, jerk 3, no initialization phase,
            100 iterations, convergence 1e-5) and none of G22's added keys: the fork as upstream
Order: Tunnel2 (78 s) with all ten; then the variants that move the score on UndergroundCarPark2 and one Beltway.
No change to G follows from this alone: a candidate needs its own preregistered rule on all development data, and a
claim needs fresh blind data.

Addendum 1 (2026-11-13, after Tunnel2 and UndergroundCarPark2 with the ten variants, before the runs below)
  Seen: no single group of G22's keys explains the gap. On UndergroundCarPark2 every variant stays between 0.1215 and
  0.1388 m (upstream 0.4.0: 0.1122); on Tunnel2 the variants scatter from 1.02 to 3.64 m, and the fork at upstream's
  defaults ("up") slips 64 m along the tunnel (32.4 m ATE) where upstream 0.4.0 has 1.26 m. So the fork at upstream's
  defaults is not upstream 0.4.0.
  Found: the fork's base is upstream 0.3.2 (48e12f9); the rival is PyPI 0.4.0. Between them upstream changed the core
  (48 commits: ICP on the right perturbation, a new convergence criterion, a quantised voxel map, deskew without a
  per-point exponential, motion prior extrapolated across a LiDAR gap, ...).
  Hypothesis: the gap to "upstream" on Odyssey is mostly 0.3.2 -> 0.4.0, not G22's keys.
  Test (p9_odyssey_dev_pypi.sh): PyPI rko_lio 0.3.2 with its own defaults (rko_upstream_0.3.2_default.yaml, "up032")
  and PyPI 0.4.0 again ("up040", must reproduce the sealed rival score) on Tunnel2 and UndergroundCarPark2, then on
  the Beltway drive of the variant runs. The hypothesis holds if up032 lands near the fork's "up" (Tunnel2: tens of
  metres; UndergroundCarPark2: about 0.125) and away from up040; it fails if up032 lands near up040.

  Conclusions: (1) G22's keys are not what loses to upstream on Odyssey (no key group closes the gap); (2) the fork's
  default voxel sampler is one upstream reverted, and it changes results by 10-50 % on this rig in both directions;
  (3) 0.3.2 -> 0.4.0 matters little here except on Tunnel2; (4) voxel 0.25 is what costs RTF and memory;
  (5) the Tunnel2 bisect and the gravity-term hypothesis were wrong (addendum 5).
  No change to G or to the fork is made here.
