Backend speed, step 3: build the loop-search source only when a query has candidates. Written 2026-11-01, before any
run of the changed code.

Why: timers in the KITTI 05 bag pass (t4v05, 540 s today) found 879 of the 1,131 loop-search queries without a
candidate, yet every query first aggregated the latest submaps (13.7 s in all) and voxel-filtered them four ways
(39.2 s in all: the registration source, its 3D-BBS subset, the latest-frame copy and its 3D-BBS subset). None of
that feeds candidate generation, which uses the descriptor databases and the submap positions only.
Change: BackendCore::searchLoopForSubmap generates the candidates first and builds the source after, only when there
is at least one candidate. The same clouds are built the same way in the same order, with the same early returns;
an early return on an empty source drops the candidate-generation log lines, as the old order (which returned before
generating candidates) gave none. The one difference left is in log lines only: when there are no candidates AND the
source would have been empty, the old code returned without the candidate-generation lines and the new code keeps
them (descriptor-based candidate generation is off in the presets; an empty source needs the latest submaps to hold no
finite point).
